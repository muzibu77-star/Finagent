# 学习笔记

## Agent 与模型服务

### 金融 Agent 是否必须接 DeepSeek API？模型从哪里来？

不必须。Agent 是模型决策、工具执行和任务状态管理的组合；模型既可以来自外部 API，也可以加载本地权重运行。把本地模型通过 HTTP 暴露出来，也不意味着请求发给了外部模型厂商。

本项目使用本地 Qwen3.5-9B 及训练得到的 LoRA 适配器，Python 代码负责检索、读取、计算和执行状态。模型来源与当前入口以 [architecture.md](architecture.md) 和 [模型配置](../configs/m0_inference.yaml) 为准。接入其他模型服务时仍需核对提示模板、工具输出合同、预算与评测结果，不能仅更换 API 地址就假定行为一致。

### Claude Code 的 harness 和 GPT/Codex 的是否不同？能否用到本项目？

核心循环相同：模型生成动作 → harness 执行工具 → 观察回填 → 再生成。差异在工程取舍，例如工具粒度、上下文怎么省、权限由谁把关、长任务怎么续。Claude Code 侧可直接观察到的机制有：专用工具与结构化参数、工具/Skill 说明按需加载、上下文自动摘要、隔离上下文的子 Agent、文件式持久记忆、权限模式与 hook。对 Codex 内部实现只有公开信息，不能当作逐项核对过的对比。

不能整体移植。通用编码 harness 是“薄 harness + 强模型”：给模型较大自由度，靠模型读懂错误信息后自我纠正。本项目是本地 9B 模型，每轮 10 次调用、8192 输入，实测固定流程优于动态流程，适合“厚 harness + 弱模型”：能由代码保证的就不交给提示词。可迁移的是具体机制而不是整套设计：一是工具拒绝时返回可操作的具体错误，而不是固定一句话；二是用受限解码在生成阶段保证工具调用格式，而不是生成后解析再拒绝；三是按资料隔离上下文，主循环只接收所需事实。有损摘要式压缩不适合财务数字，本项目已有的无损去重更合适；按需加载工具对仅 5 个工具的场景没有收益。持久化、幂等、取消恢复、范围约束和冻结验收是本项目已有且更严格的部分。任何迁移都改变生成或上下文合同，须按新实验臂做开发对照和未暴露的验收，现状见 [architecture.md](architecture.md) 与 [result.md](result.md)。

### 两个编码 Agent（Claude 与 Codex）能否自动形成“派工 → 执行 → 验收”的工作流？

可以，关键是只设一个驱动方并串行执行。Claude 写任务文件后，用 `codex exec` 非交互地启动 Codex 执行；Codex 结束时 Claude 收到通知并验收，然后写下一步。这样不需要定时轮询，两个 Agent 也不会同时改同一个工作区。任务文件里的状态字段就是两者之间的交接协议。需要设置的边界有：需要用户拍板的事项不自动推进；不提交、不训练、不调用付费 API；设单轮任务数上限和失败即停的规则；循环只在 Claude 会话开着时运行。定时检查文件只是退路：它有空转成本，还可能和执行中的 Codex 读写冲突。

### 复查 Agent 能找出错误，为什么却报不对事实编号？

- 找错靠理解（读表、对科目、换单位、比大小），这是模型擅长的；编号是没有语义的标识符，要从几十轮工具记录里一字不差地抄回来，模型容易丢、容易混。T19c-2 实测：Agent 判出 764.21 应为 764.47 亿元，页码和原文都对，`refs` 却写成 `"f1"`。
- 格式里同时有 `refs`（编号）和 `formula` 里的 `f1`、`f2` 两套记号，模型把两者混在一起，这是格式设计的问题。
- “判正确或错误必须给编号、判无法判断不用给”给了模型一条退路，报警数从 285 降到 222，判出率随之下降。附加在答案上的要求，会改变模型的主要行为。
- 原则：判断交给模型，记账交给代码。模型用了哪条事实，应从工具调用记录中由代码取出，而不是让模型在答案里自己报。

## 训练与评测

### 为什么金融 Agent 准确率低，怎样证明优化有效？

给定证据计算、文档 RAG 和自主多轮任务的难度与分母不同，不能混成一个准确率。当前开发轨迹确认上下文重复膨胀、压缩后动作/观察角色丢失伴随重复调用；扩量 SFT 的参考事实筛选与推理全事实输入不一致，是需要对照验证的回退原因，不能直接断言是唯一根因。改进依次验证无损去重、真实工具交互上下文、部署一致的监督和执行偏好训练；以当前最好模型为主参照，固定评分、报告失败与配对置信区间，仅用开发集选型。ReAct 强调动作与环境观察的交互（https://arxiv.org/abs/2210.03629）；DPO 使用偏好对而非直接在线工具奖励（https://arxiv.org/abs/2305.18290），两者均不保证在本项目自动带来收益。

补充：数字相关度截断可能移除低词面重合但计算必需的总额/分母；上下文压缩应优先消除重复原文和冗余交互，保留完整事实及工具角色。开发诊断中修复有所改善，仍须完整开发集和冻结验收确认，不能把执行完成率当作答案准确率。

补充：计算器只能保证已给定公式的执行，不能保证模型选对事实、期间、正负号或公式；多步任务应单独分层。严格输出合同也会造成独立失败，例如答案中加入了评分器不允许的额外字段。应通过更明确的提示做独立对照，保留原严格评分；不能靠忽略格式、自动乘除 100 或只报低难度题来制造提升。

### 第五版验收"复杂任务变好却整体不通过"说明了什么？

主指标的配对区间为正，但"单题不降"用的是 30 道题上的点值比较：19 对 18，实际是得 1 题、失 2 题。一道题就是 3.3 个百分点，而同一输入重复生成本身就会让 1—2 题翻转，所以这种门槛在候选与基线真实水平相同时也有相当概率判负。教训有三条：护栏指标也要按样本量设计，用事先写明的非劣界值或区间代替点值比较；一次验收里同时改了训练数据、历史算式、常量和报错方式，结果就无法归因到其中任何一项；提示层的报错改进对没有按它训练过的权重无效（验收中略负），开发集上"看起来无害"不能代替验收。门槛写错了也不能事后改，只能在下一次验收前改写规则。

### "提升相对噪声偏小"是什么意思，原因是什么？

噪声指"真实水平没变，分数自己也会晃动"的幅度，来源有三个：题目是抽样来的（换一批题分数就不同）；题数少（93 道题时 1 题就是 1.1 个百分点，30 道题时是 3.3）；同一输入重复生成也会有 1—2 题翻转。置信区间就是把这种晃动量出来的范围。第五版主指标点差 +9.7 个百分点，区间 [+1.2,+18.1]：下界离 0 很近，说明"确实变好了"勉强站得住，但真实提升可能只有 1 个点也可能有 18 个点。原因是效果本身不大（约 9 题），而题数只有 93、其中还有得 11 失 5 这样的来回翻转。要让结论更稳，只有两条路：把效果做大，或把题数加多；区间宽度大致按题数的平方根收窄，题数翻四倍区间才窄一半。

### 为什么一次只能改一个因素？

同时改四样东西，结果变好时不知道是哪一样起作用，变差时也不知道该撤哪一样，而且有害的改动可能被有益的掩盖。第五版就是这样：新权重同时带了更多数据、历史算式、官方常量和报错提示，唯一拆得出来的"只改提示层"在验收里略负，其余三项的贡献无从分辨。正确做法是固定基线，每个对照只动一处，需要重训的因素各自单独重训；只有在各因素都有独立证据之后才组合，并把组合当作一个新的因素再验证一次。代价是每个因素都要一次完整的训练和评测，所以要先用便宜的大样本开发工具筛选，再把昂贵的验收留给筛出来的候选。

### 为什么一次重训要几个小时？

训练用时与总输入 token 数成正比：本项目实测约每秒 415 个 token（前向加反向），第四轮 399 万 token 用 2.7 小时，第五轮 1,069 万 token 用 7.4 小时。慢的原因有四个。其一，每个样本带着整页财报（平均约 2,900 token），而被监督的只有末尾约 50 个 token（约 2%），同一页还会随每个动作重复编码；这是让训练上下文与部署完全一致的代价。其二，24 GB 显存装 9B 模型后余量很小，只能单样本前向、累积 8 次再更新，长样本还要把激活暂存到内存。其三，模型的一部分层因缺少加速库而退回慢速参考实现。其四，为可复现开启了确定性算子。所以缩短时间的办法是：验证单个因素时用小规模数据，确认有效再跑全量；只对确实放不下的长样本做内存暂存；在获得授权并重新验证数值后再考虑安装加速库。

### 多卡训练为什么要和单卡保持同一个训练过程？

多卡是为了让同样的训练跑得更快，而不是换一种训练。如果每张卡各算一整批，一次更新的样本数就变成原来的若干倍，更新次数和学习率的实际效果随之改变，训出来的是另一个模型；用它去和单卡基线比较，差别里就混入了训练方式这个额外因素。保持同一过程还有两个好处：单卡结果成为检验分布式实现的标准答案（梯度该求和却取平均、样本重复或遗漏、调度多走一步等错误都会在对照中暴露），以及检查点可以在不同卡数之间续训。本项目的做法是一次更新仍用固定顺序里相同的 8 个样本，各卡分摊计算、梯度求和后执行相同的优化器步，即 global_batch = 1 × (8 / 卡数) × 卡数，差别只剩浮点求和顺序。放大批量并相应调整学习率是另一种合法的配方，但需要重新调参和验证，应作为独立实验。

### 现在的多卡训练算哪一种分布式？

单机多卡、同步、数据并行：每张卡一个进程、各持一份完整模型，一次更新的样本按卡分摊，各进程前向反向后通过 NCCL 做一次梯度 all-reduce，再各自执行相同的优化器步，所以各卡权重始终一致。这与 PyTorch `DistributedDataParallel` 的机制相同；区别是梯度同步由手写的 all-reduce 完成，并且只在一次更新的全部样本累积完后同步一次（相当于 DDP 在累积期间使用 `no_sync()`）。它不是多机集群训练（没有在多台机器上验证过），也不是把单个模型拆到多卡的模型并行或 FSDP/DeepSpeed 式的参数分片。4 卡实测加速 2.6 倍而不是 4 倍，因为每次更新要等最慢的那张卡，而样本长度不均。

### 为什么用数据并行而不是模型并行？

模型并行把一个模型的不同层放到不同显卡上，解决的是单卡装不下的问题；一个样本要依次流过各张卡，任一时刻只有一张卡在计算，所以它本身不提速，还要付出跨卡传输的代价。数据并行是每张卡一份完整模型、各算不同样本，解决的是吞吐。本项目的模型权重约 17.5 GB，24 GB 的卡装得下，因此选数据并行。但"装得很挤"有代价：梯度检查点重算和激活内存暂存合计拖慢四到五成。所以一种可能更快的混合方案是每份模型占两张卡（显存宽裕，去掉省显存的手段），四张卡跑两份；这只是估算，需要实测并重新验证数值，当前不是优先事项。

### 为什么复杂任务（跨报告/多轮）的通过率一直上不去？

复杂任务要求每一步都对，所以它的通过率不会高于最弱的一步；第四轮之后流程类问题（预算耗尽、拒绝生成、重复检索、读错页面）已基本消失，剩下的失败几乎都是"合法执行但数值错"：取错单元格、公式不对、百分比/量纲/正负号口径不符。这是模型读表取数的能力（连只需取一个数的轮次也只有约 64% 通过），不是 Agent 循环的问题，所以只改 harness、加历史算式、多次作答取多数都不起作用。教训：复杂任务的指标是结果而不是抓手，应先把失败按"流程 / 取数 / 公式 / 口径"分层，确认瓶颈在哪一层再选改动。数字来自开发集的事后归类，分类边界是近似的，见 [result.md](result.md) 与 [progress.md](progress.md)。

更正（2026-10-13）：最初写的"通过率约等于单步准确率的连乘"不准确。连乘假设各步独立，而实测错误集中在同一批难页面上：79 段对话按独立连乘只应全对约 17 段，实际 29 段。正确的写法是条件概率的链式乘积（首轮通过率 × 前面全对时后续轮的通过率），用独立连乘反推"单步要到多少"会高估所需水平。

### 多轮里"前面错了后面也错"是错误传播吗？

大部分不是。前面出过错的对话里，后续轮只有约 24% 通过，但不依赖前轮的后续轮同样是 24%；把同一道题单独拿出来问，这批题也只有约 43%（前面全对的那批是 71%）。也就是说，首轮出错主要是在提示"这一页本身难"，属于选择效应；真正由对话上下文带来的额外损失只是其中较小的一部分。依赖前轮的失败里，多数是把同一个错数再用一遍，这是一个错误被数了多次，而不是产生了新的错误。判断"传播"之前要先做这种对照：同一道题脱离上下文单独测一次，否则会把题目难度误当成传播。

## 业务价值与产品定位

### 当前项目对金融从业者有什么意义、有什么用？

适合定位为由专业人员复核的财报取数与计算助手：为研究、信评和尽调中的局部问题提供候选数字、计算过程与原文依据，潜在价值是减少找资料和核对来源的时间。可追溯不等于语义正确，计算器也不能保证指标、年份、单位和公式选对；当前服务范围与实验能力须分开，事实边界见 [architecture.md](architecture.md)，质量证据见 [result.md](result.md)。不能据基准提升宣称已经能独立完成研究、信用判断或投资决策。业务价值需要用真实从业者任务验证：在相同质量要求下，比较纯人工与辅助流程的总耗时，计入复核、纠错和返工，并检查最终错误率。工程和模型实验的进展本身不能代替这一证据。
